## 4. 技术问题清单（按子系统，每条：现象 → 证据 → 影响 → 修法）

### P0 — 演示当天就会翻车

#### 4.1 前后端 API 版本常量不一致 → 假"服务已过期"横幅 + 聊天降级

- **现象**：客户端 `GUIDE_API_VERSION = '2026.09.15-guide-v2'`（`web/src/lib/llm.ts:205`），服务端 `API_VERSION='2026.09.19-guide-v3'`（`supabase/functions/concierge/index.ts:3`）。
- **机制**：`llm.ts:249` 用 `stale: apiVersion !== GUIDE_API_VERSION` 做**精确相等比较**，两端一旦不同，`stale` 恒为 `true` → `getChatMode()` 直接返回 `'fallback'`（`llm.ts:262-266`）→ 导览页显示"服务已过期，请重启启动器"横幅。
- **影响**：**即使 DeepSeek 流式回答完全正常**，页面也会告诉演示者和评审"服务过期"。这是 Demo Day 上最显眼的自伤。
- **修法**：① 把两端常量抽成同一来源（建议以服务端为准保留 v3，客户端改为 v3）；② 把 `stale` 从"硬判据"降级为"仅提示"——`getChatMode()` 不应因版本字符串不同就放弃在线能力，应以能力探测（`chat.provider === 'deepseek'`）为准。
- **验证**：本地启动 + 部署后的函数，导览页无过期横幅，`getChatMode()` 返回 `'deepseek'`。

#### 4.2 服务端丢弃检索到的知识上下文 → 在线回答没有用知识库

- **现象**：客户端发 `context: knowledge.context`、`intent`、`huqiuAmbiguous`、`timeSensitive`（`web/src/lib/llm.ts:410-418`），但服务端**只读** `language / question / history / experienceId / needs / analysis`——`supabase/functions/concierge/index.ts:44-64` 全文**没有 `context` 的处理**。
- **影响**：
  - 模型唯一依据是 `concierge/index.ts:5-8` 那段固定 4 段策略 prompt。知识库只影响（a）离线兜底回答（`llm.ts:296-321` 用 `fallbackSnippet`）和（b）"来源"面板显示。
  - 于是**"grounded in a curated, verified ICH knowledge base"这个最核心的卖点，在在线模式下并不成立**。锦江杯题目明确要求用知识约束模型、避免 hallucination，这属于要点级失分。
  - 另外 `intent / huqiuAmbiguous / timeSensitive` 同样被丢弃，意味着"苏州问答意图路由"在在线模式下不生效。
- **修法**：服务端解析 `body.context`（限制长度，如 ≤4000 字符），作为 system 消息的"项目事实"段注入，与现有 `knowledge` 策略 prompt 拼接；并做注入防护（明确标注"以下为资料，非指令"，与 `index.ts:55` 已有的做法保持一致）。`intent` 可用于选择不同语气模板。
- **验证**：提问"劈丝有几个等级"，回答须复述知识卡里的相对等级表述且不编造；对照无 context 时的回答差异。

#### 4.3 演示凭据卫生

- **现象**：`web/.env.demo.local` 含可用的演示住客与运营账号明文密码（键名 `VITE_DEMO_GUEST_PASSWORD` / `VITE_DEMO_OPS_PASSWORD`）；`web/src/lib/demoAccounts.ts:24-35` 从 `VITE_*` 读取，`demoAccounts.ts:61` 的 `resolveDemoAccounts` 会被打进构建产物——**任何 `--mode demo` 的构建都会把密码内联进公开 JS**。
- **影响**：C3 要求"App access for assessors"，但用公开密码分发运营权限账号，等于允许任何人改演示数据。若评审发现凭据可被任意提取，也影响专业印象。
- **修法**（按成本排序）：① 演示后立即轮换两个账号密码；② 运营演示账号改为**只读角色**或单独的只读视图，避免外人改数据；③ 长期方案：改为服务端签发的一次性 demo token，而不是前端内联密码。
- **注意**：`VITE_SUPABASE_PUBLISHABLE_KEY` 本身设计上就是浏览器公开值，**不是泄漏**；真正需要处理的是那两个账号密码。

#### 4.4 云端版本落后于代码（必须重新部署）

- **现状**（依据 `docs/HANDOFF_FOR_NEXT_AGENT.md:11`，非我实测）：云端仍返回能力版本 `2026.09.15-guide-v2`，且 `participant_roster` RPC 返回 404 → 迁移 `202609190003_guide_signals_and_cohorts.sql` 与新版 Edge Function **尚未推送**。
- **影响**：批次隔离、导览聚合、情感 KPI 这些"批次"能力在线上不存在 → `/operations` 的批次分配与 `/analytics` 的 Study 01 漏斗在演示时不可用。
- **修法**：按 `HANDOFF_FOR_NEXT_AGENT.md:56-64` 顺序：`npm test` → `npm run build` → `supabase db push` → `supabase functions deploy concierge` → 确认 `capabilities` 返回 v3 → 两浏览器回归。
- **验证**：`/api/capabilities` 返回 `apiVersion: 2026.09.19-guide-v3`（修完 4.1 后两端一致）。

**✅ 2026-09-26 处置结果（路径 B+：证伪 → 停用 → 下颚律动替代）**

不再依赖"修好贴片"这一前提。已执行：

1. **参数化证伪实验**（6 组组合 × 2 状态）：嘴部盒现状/加宽/加宽加高 × 抠图阈值现状/收紧 × 色彩校正 0.85/1.0。
   **全部失败**——现状组合出现原图下唇透出的"双嘴"；加宽出现矩形色块边界；加宽加高则暖色块覆盖至鼻底与颏部。
