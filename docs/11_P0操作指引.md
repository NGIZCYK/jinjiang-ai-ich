## 三、10+ 名真实用户测试(Study 01)

### 目标

- Week 3-4:pilot 3-5 人,验证流程可走通、脚本可执行;
- Week 8-9:累计 ≥10 人(冲刺 12-15 人留冗余),其中 ≥8 人"无协助"走完全流程,产出 User Testing Report。

### 招募渠道(按优先级)

1. 同楼层/同班同学 + 宿舍邻居(酒店住客画像最接近的"普通游客");
2. 团队 6 人各自邀请的家属/朋友(视频远程亦可,屏幕共享操作);
3. 社团/班级群发招募帖(附 10 分钟时间段选项)。

筛选要求:注册批次统一选 `Study 01`(看板按批次去重);每人事后填统一反馈。

### 测试脚本(每人 15 分钟,照读)

1. **开场(1 min):**"这是一个酒店里的苏绣文化礼宾原型,不是真实酒店服务。请像在自己入住时一样使用,全程请不要我们提示。"——征得同意后录屏(证据)。
2. **自由探索(4 min):**给手机/电脑,只给入口地址,观察能否自主注册登录、进入导览。记录卡点。
3. **任务(6 min,按 docs/03 动线裁剪):**
   - T1:向婉娘提问"我带孩子,下午有 2 小时,预算 150,想体验苏绣";
   - T2:在沉浸角完成一张探索卡并提交;
   - T3:查看推荐并提交体验意向;
   - T4(运营端演示,不要求用户操作):展示 ops 确认后用户收到状态变化。
4. **回访(3 min):**三个固定问题——哪里最吸引你?哪里让你困惑?你愿意为 90 分钟工坊付 ¥128 吗?为什么?
5. **数据留存:**录屏文件 `Study01_用户编号_日期.mp4`;现场记录表(下方模板)当周归档。

### 现场记录表模板

| :-: | :-: | :-: | :--- | :-: | :--- | :--- |

## 四、密钥轮换(CHANGELOG 2026-09-19 遗留待办)

> 背景:跨设备验收期间多个 Supabase access token 与 DeepSeek key 曾在本地文件中流转;验收完成后应全部轮换,并作废 `web/.env` 中的历史旧 key。

### 步骤

1. **DeepSeek key 轮换**:登录 DeepSeek 开放平台 → API Keys → 删除旧 key → 新建 → `supabase secrets set DEEPSEEK_API_KEY=<新key>` → 用 `/guide` 验证在线回答正常 → 确认旧 key 已失效(用旧 key 调一次 API 应 401)。
2. **Supabase access token 轮换**:Supabase Dashboard → Account → Access Tokens → 撤销旧 token → 新建;本机执行 `supabase logout && supabase login` 更新本地凭据。
3. **清理 `web/.env`**:确认只保留 `VITE_SUPABASE_URL` 与 `VITE_SUPABASE_PUBLISHABLE_KEY`(两者本就是浏览器公开值);删除其中任何历史遗留的 DeepSeek/service-role 类条目。
4. **检查 Edge Function secrets**(`supabase/functions/.env.example` 对照):`DEEPSEEK_API_KEY/MODEL/BASE_URL`、`ALLOWED_ORIGINS`(与正式访问域名一致)、可选 `AZURE_SPEECH_KEY/REGION/VOICE_ZH/VOICE_EN`。
5. **验证**:跑一遍 `docs/03_演示脚本与账号.md` 第三节 1-8 步;`npm test` 全绿。
6. **归档**:在 CHANGELOG 追加一条轮换记录(日期+范围,不写密钥值);确认 `.gitignore` 覆盖 `web/.env` 且 git 历史无真实密钥(如历史提交中出现过,记录待办并在报告中说明已作废)。
